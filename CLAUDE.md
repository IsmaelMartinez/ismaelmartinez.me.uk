# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # Start development server
npm run build        # Build for production (output in ./dist)
npm run preview      # Preview production build
npm run lint         # ESLint across the repo
npm run typecheck    # Astro + TypeScript check
npm test             # Run Vitest suite (build tests require ./dist to exist)
npm run check-links  # Validate internal links in ./dist (run after build)
```

## Architecture

This is a multilingual Astro static site with three supported locales: English (en), Spanish (es), and Catalan (cat). The site uses file-based routing with locale prefixes (all pages live under `/en/`, `/es/`, `/cat/`).

### Internationalisation

The i18n system centres on `src/i18n/translations.ts`, which exports the `useTranslations(lang)` function used throughout components. Every UI string is keyed in this file across all three locales. The `getLangFromUrl()` and `getLocalizedPath()` helpers handle routing between language versions.

Pages are defined once under `src/pages/[lang]/…` as dynamic routes that use `getStaticPaths()` to emit `/en/`, `/es/`, and `/cat/` variants (see `docs/plans/2026-02-15-phase4-security-maintainability-design.md` for the deduplication rationale). The root `src/pages/index.astro` redirects to the default locale (`/en/`), and `src/pages/404.astro` is the shared 404.

### Content

Static data (projects, links, health, person) lives in TypeScript files under `src/data/` with inline translations per object. Articles use Astro Content Collections in `src/content/articles/{locale}/` with MDX format. The schema is defined in `src/content.config.ts` (Astro 6's top-level content config location).

Articles follow POSSE (Publish Own Site, Syndicate Elsewhere) strategy per ADR 001 in `docs/adr/`. Frontmatter includes `originalUrl` and `originalPlatform` to link back to syndicated copies on Medium/Dev.to.

### Arcade games

Arcade pages live under `src/pages/[lang]/fun/`. Newer games (Tank Duel, Pixel Park (parked off the floor, see below), Microcity, Line Hold, Cascade) split pure game logic into DOM-free TypeScript modules under `src/games/<game>/` (unit-tested in `tests/games/`) with a single `init<Game>()` entry the page calls; shared utilities (fixed-timestep loop, hi-DPI canvas setup (`canvas.ts` — DPR-scaled backing store with a logical-coordinate contract; pointer math must use its `toLogical()`, never `canvas.width`), top-10 high-score tables with arcade initials entry (`highscores.ts` + `scoreboard.ts` + `src/components/HighScoreTable.astro`), where each cabinet's panel shows one board, the global one every visitor shares (a Vercel Function at `api/scores.ts` over one Vercel Blob JSON file per game, with the client seam in `src/games/engine/globalScores.ts`; the decision to run this on the Vercel deployment the site already has, why an earlier Cloudflare recommendation was reversed, and why the per-device board that used to sit beside it under a pair of tabs was removed on 2026-07-29, are all recorded in `docs/adr/002-global-arcade-high-scores.md`), grid helpers, shared BFS pathfinding (`pathfind.ts` — a walkability predicate over the flat grid; Pixel Park, Syndicate, and Line Hold all route through it), isometric renderer) live in `src/games/engine/`. Three engine modules are the *required* channel for game feedback — new games must not re-paste them: `toast.ts` (`createToaster` — DOM toast stack, cap 3, timed auto-remove, swap-safe timers), `effects.ts` (`createEffects` — canvas particle bursts + text floaters; per-game constants go in as construction options, bespoke spawn math hands finished particles to `emit()`, and a copy that genuinely can't fit the options stays local with a comment naming the divergence — today only Critter Rescue's), and the scoreboard's run-record API (`beginRun()` at run start, `bank(score)` on every gain → `{ best, newRecord }` for the HUD readout and the one-time record toast, `best()` for init-time HUD seeding). Render loops must not rebuild static full-canvas content (starfields, checkerboards, vignettes) per frame: bake it with `createStaticLayer` in `canvas.ts`, rebuilt via `setupHiDpiCanvas`'s `onApply` (its JSDoc carries the device-pixel alignment contract). The one exception is a full-canvas gradient fill that doubles as the frame clear (the sims' skies), which keeps a hoisted `CanvasGradient` instead. The iso cabinets' shared drawing idioms also live in the engine and are the required channel — don't re-derive them per game: `blockFaceCorners`/`blockSeamPath` in `iso.ts` (inset footprint corners + the W→S→E course line across a block's visible faces), `faceBandPath` (the interpolate-along-projected-edge quad behind shopfront glass, office strips, counter bands, and two-edge awning canvas; path-append so callers keep their own fill batching), and `blink` beside `hash01` in `canvas.ts` (the 1.5 Hz rooftop-beacon cadence, phase-offset by tile index). Geometry that is a pure function of slow-changing state gets cached, not recomputed per frame: Microcity memoizes per-tile hashed variety (hash rolls + derived colour strings) per `type:level` key — from the 2026-07-20 consolidation round (`docs/plans/2026-07-20-arcade-consolidation-2-drawing-idioms.md`). (Pixel Park once baked per-track-tile rail geometry into a `railCache` here too; that cache retired with the lay-your-own-track coaster — see Round 12.) Render refactors that must not change output are verified byte-identically with `scripts/screenshot-games.js` (deterministic seeded-PRNG + stepped-rAF captures; not in CI — see its header for the ad-hoc setup). Static labels render server-side via `useTranslations`; runtime-composed strings pass through `data-t-*` attributes on the game root. New games register a cabinet in `src/pages/[lang]/fun/index.astro`, which groups the floor into two labelled shelves since Round 6's owner-approved focus decision — a front **Featured** shelf (Syndicate, Line Hold, Critter Rescue, Cascade) over a **Back catalogue** shelf (Microcity, Tank Duel, Snake) — each `arcadeGames` entry carries a `shelf` key and the shelf signs use the `fun.arcade.shelf.*` i18n keys. Pixel Park is currently **parked** (2026-07-27): its cabinet is removed from `arcadeGames` and its page is fully unpublished — renamed to the underscore-prefixed `src/pages/[lang]/fun/_park.astro`, which Astro excludes from routing, so no `/fun/park` page is built or listed in the sitemap. Its `src/games/park/` modules and the page source both stay in the repo; to revive it for a future release, rename `_park.astro` back to `park.astro` and re-add its `arcadeGames` entry. Line Hold (tower defense, `src/games/towerdefense/`) and Cascade (falling-block stacker with cascade-gravity chains, `src/games/cascade/` — its pure run state machine in `run.ts` lets tests play whole games headlessly) both shipped from `docs/plans/2026-07-12-next-arcade-game-design.md`. (Cascade renders as a flat top-down well, not the engine's isometric view — it is a newer cabinet by architecture, not an iso one.) CALCIO '90 (top-down seven-a-side football, `src/games/football/`) is the arcade's most module-split cabinet and the only one that renders through a **framebuffer**: everything is drawn into an offscreen 320 x 224 canvas (the Mega Drive's H40 resolution) with `imageSmoothingEnabled = false` and blitted to the visible canvas at the largest whole scale that fits, so `game.ts` performs exactly one draw per frame and no game pixel is ever resampled. That last clause is only true because the canvas box is sized in **device** pixels by `game.ts` rather than by CSS: `render.ts`'s pure `integerScale(availW, availH, dpr)` picks the largest whole multiple of 320 x 224 that fits the container, the backing store is set to exactly that, and the CSS width is the backing store divided by `devicePixelRatio` so the two agree to a fraction of a device pixel. The stylesheet must therefore never give `#game-canvas` a `width` or an `aspect-ratio` — a `width: 100%` box inside the 720 px container is what put a 960-wide framebuffer into a 716 px box, a 0.746x nearest-neighbour downscale that dropped a quarter of the framebuffer's rows and columns and showed up as uneven stems on the wordmark and the HUD. This cabinet is also the one place `setupHiDpiCanvas` is deliberately not used, for the reason written at `fitCanvas`: its contract is that CSS owns the box and it clamps the ratio at 3, and here neither holds. `font.ts` ships a 5x7 bitmap font drawn with batched `fillRect` runs — the cabinet never calls `fillText`, which would be the one anti-aliased thing on screen — and covers the accented capitals Spanish and Catalan need, with `tests/games/football-render.test.ts` asserting that every `fun.football.*` string in all three locales has a glyph and that no source file carries a hex literal off the Mega Drive's 3-bit ladder. The DOM-free modules are `pitch.ts` (geometry, formation anchors, the pure `cameraFor`), `teams.ts` (twelve invented sides, eight drawn per run), `match.ts` (ball with a real height axis, possession, the three stoppages, the compressed 0'-to-90' clock), `keeper.ts` (a **probabilistic** keeper — being within reach is a save *roll*, never a certainty, which is the direct regression against the previous build's deterministic absorber), `ai.ts`, `setpieces.ts`, `shootout.ts` and `tournament.ts` (two groups of four, 2-1-0, top two through, semi then final, plus `runScore` as the single place the run's number is computed). Celebrations are pixel-native: the engine's `createEffects` stays the required channel for the *physics* (`burst`, `emit`, `update`, `clear`) but `renderer.drawEffects` reads its arrays and rasterises them itself, because the engine draws floaters with `ctx.fillText` in a system font and fades both kinds under `globalAlpha`, and 8.1 forbids anti-aliasing and alpha blending in the pixel layer — a particle is a whole-pixel square that flickers off on alternate frames near the end of its life (how the hardware faded a sprite), and a floater is a bitmap word. Two cabinet features live outside the specification. **Attract mode** (`demo.ts`): after `ATTRACT_DELAY` (12 s) idle on the title screen the machine demos itself, and it is the ordinary `MatchState` stepped by the ordinary `tickMatch` with a driver supplying side 0's `MatchInput` from the same `ai.ts` the CPU thinks with — not a second simulation. It is seeded (`seededRng`) so a demo replays from its number, it holds its match in its own `demo` variable so no full-time path can reach a `RunState` and neither the scoreboard nor the personal best is ever touched, it stops stepping when `document.hidden`, any input at all discards it, and when a demo match ends it returns to the title and starts another. The only place the driver overrules `planCarrier` is when to shoot, because the CPU's gate wants a clean corridor and a shop window wants shots. **The hidden team**: `SECRET_TEAM` (FEN, Fenice, 5/5/4/4) sits outside `TEAMS`, so it is never drawn as an opponent and never on the select grid until the Konami code unlocks it there; the unlock is remembered in `arcade-unlock-football` and the flourish is a bitmap banner plus a cue. That code is also why the cabinet's `keydown` listener is on `window` in the **capture** phase and stops propagation for the keys it consumes: the layout's own site-wide Konami handler listens on `document`, and without the capture both eggs would fire at once. The capture yields to the page for text fields entirely, and to a focused button or link for the two keys that activate it, so the high-score initials box and the sound toggles still work. `game.ts` owns the screen flow, keyboard and touch input, the loop, the audio and the scoreboard; its page `src/pages/[lang]/fun/football.astro` currently ships **unlisted** — no `arcadeGames` entry — because the floor is being rebuilt in a parallel PR, so it gets its cabinet slot in a follow-up. The acceptance gate is `tests/games/football-balance.test.ts`, which plays 300 seeded matches per difficulty cell with four scripted players from `tests/games/football-policies.ts` plus 200 whole runs per policy, and asserts the whole of the rewrite specification's section 7. Two things about it are load-bearing. It contains **no assertion that the human does not win** — the suite it replaced asserted `expect(m.score[1]).toBeGreaterThanOrEqual(m.score[0])`, encoding the shipped bug as the specification — and **no test may bench, park or disable a keeper in order to score**. Four of the specification's flow targets are asserted at the values the cabinet actually reaches rather than the ones it asks for, each carrying a `DEVIATION` comment with the measured figure and the arithmetic behind it: the cross/header goal share (0.05-0.10 against a 0.15-0.40 ask, though the 0.45 anti-hoof ceiling holds), ground-pass completion (0.48-0.56 against 0.60-0.85), the average possession spell and the turnover count (1.0-1.2 s and 26-29 against 2.5-6.0 s and 12-26, which cannot coexist with eight shots a match in sixty seconds), the champion rate (0.38 against 0.12-0.32, which is qualification times two knockout ties and so is bounded below by the same section's own per-match win-rate floors), and the group-exit run length (4.1 min against 2.5-3.5, when three sixty-second matches are 3.0 min of football before a single stoppage). Difficulty is the **CPU's** handicap and never a global dial: the player's own keeper sits at a fixed `HUMAN_KEEPER_PROFILE` and the human side always presses with two, while the CPU's second presser, slide willingness, decision latency, pass and shot accuracy, directness and keeper skill are the only channels it flows through. Poo Poo Land was retired in the 2026-07-19 consolidation round (`docs/plans/2026-07-19-arcade-consolidation-plan.md` — it predated the architecture; its localStorage data and legacy key-migration entry survive in case it ever returns as a rebuild). all eight cabinets were then re-scored to bespoke multi-voice arrangements: Pixel Park a 3/4 carousel waltz, Syndicate Blade-Runner dread, Cascade a Korobeiniki-style minor that keeps its per-level `setTempo` ramp, Snake kept deliberately minimal), and Round 12 from `docs/plans/2026-07-25-park-coaster-placed-ride-plan.md` (Pixel Park's roller coaster stopped being a drag-to-build loop of `track` tiles with a `Coaster` runtime, cart, queue and geometry validator — the whole of `track.ts` plus ~800 lines of drafting and rail/cart rendering in `game.ts` were deleted — and became an ordinary `thrill` building that occupies a 2×2 footprint. The load-bearing new idea is a minimal footprint concept in `grid.ts`: `footprint?` on `BuildingDef`, `footprintTiles`/`footprintOf`, with single-tile placement left arithmetically byte-identical. The `coaster` `BuildingDef` is the best thrill in the park (`boost` 100); `applyTool` writes an anchor tile plus three inert `rideannex` fillers and bulldoze clears the whole footprint from any of the four; `adjacentWalkable` spans the footprint so guests approach from any side; and a `drawCoasterRide` sprite paints over the footprint in a post-pass (it is not an in-loop block). The Pirate Ship stays the single-tile thrill option; the coaster is the premium 2×2 one that "just works" — no track laying, no up/down).

Scoring conventions across the cabinets: there is **one board**, the global one every visitor shares, served by a Vercel Function at `api/scores.ts` backed by Vercel Blob (client seam `src/games/engine/globalScores.ts`, submission wired into `scoreboard.ts`'s `commit()`; the rejected alternatives and the Cloudflare-to-Vercel reversal behind this choice are in `docs/adr/002-global-arcade-high-scores.md`, whose "Corrections from production" section records what running the write path for real disproved: `put` has no conditional *create*, so an absent read is never taken at face value; it also records that the CDN does cache the read on plain `max-age`, measured against the deployed endpoint after a review claimed otherwise, so `s-maxage` is belt-and-braces rather than load-bearing). What `highscores.ts` still keeps on the device is only the last-used initials and a **personal best number per game** (`loadBest`/`saveBest`, key `arcade-best-<gameId>`, migrating once from the retired `arcade-hs-*` tables and then from the pre-table single-number keys); that number is what `best()`, the HUD readouts, the record toast, and the arcade floor's attract screens read. Four rules here are load-bearing and easy to undo by accident, so do not re-gate them. **Every finished run with a score above zero is submitted** — `qualifies()` decides only whether the player is interrupted for initials, never whether the run reaches the board, because gating the submission on a private table is exactly the bug that left eight of the nine live boards holding a single entry each (regression pinned in `tests/games/scoreboard-dom.test.ts`). The board is **refetched at panel init and again at every run end**, since a player has no refresh button and a once-only load froze the shared board for a whole session. And both a fetch's reply and a submission's own reply are ordered by the single `worldGen` generation that only a submission bumps, so an overtaken or out-of-order answer stands down instead of putting an older board back on screen. Finally, **a submission that does not land says so** in the panel note (`fun.arcade.scoreNotSaved`), because with no device table behind it a failed write loses the run outright; the notice is gated on `canSubmit()` so local dev and previews, which read the board but never write to it, stay quiet rather than crying wolf. `commit()` records the finished run through the run record's `bank()` rather than writing `saveBest` behind its back (so `best()` and storage cannot disagree mid-session), and fires `onSave` once per committed run whatever became of it, with rank 0 when it did not chart or did not land. Server-side, `top` is the **persisted all-time top ten**, merged per write by `mergeTop` rather than re-derived from a rolling history (which silently expired records once a board passed the history cap), and one pruned `recent` array carries replay dedupe plus both rate limits. Beyond that: games whose runs can be long (Microcity, Pixel Park, Syndicate, Line Hold, Cascade, CALCIO '90 — the latter on every goal and every stage transition, through `tournament.ts`'s `liveGoals`, which is what lets `runScore` stay the only place the number is computed while still growing mid-match) bank the run's best as it grows — `bank(score)` stashes automatically — so a closed tab never loses a record; every point gain is announced on screen the moment it lands (canvas floaters/score popups via `createEffects`); the number a finished run submits is shown to the player rather than computed silently (e.g. Tank Duel's match score, Critter Rescue's bonus breakdown); and beating the personal best mid-run earns a one-time toast driven by `bank()`'s `newRecord` flag; Critter Rescue is also long-run but banks on level-clear only, and never calls `beginRun()`, which leaves the celebration unarmed so it fires no mid-run record toast. `bank()` is the **only** write path to the persisted best: the `Scoreboard` interface deliberately exposes no second verb for it, so the number in memory and the one on disk cannot drift apart.

### Layouts and Components

`src/layouts/Layout.astro` is the base layout with navigation, language switcher, and footer. `src/layouts/ArticleLayout.astro` handles article pages. Components in `src/components/` are shared across locales.

### Testing & CI

Vitest tests live under `tests/` (unit tests for i18n and reading-time, the arcade game-logic suites under `tests/games/`, plus `tests/build/output.test.ts` which reads files from `./dist` and is skipped unless a build has been produced). Vitest runs in the node environment with no DOM: neither jsdom nor happy-dom is installed, so DOM-wired engine modules (`scoreboard.ts` above all) have no unit coverage, and changes to their wiring are verified in a browser against `npm run dev` rather than asserted in a test. The link checker in `scripts/check-links.js` walks built HTML in `./dist/` and verifies internal hrefs resolve to real files. CI (`.github/workflows/ci.yml`) runs lint, typecheck, build, tests, and link check on pushes to `main`/`develop` and PRs to `main`.

### Deployment

The deploy workflow (`.github/workflows/gh-pages.yml`) runs after a successful CI on `main` (and on a six-hourly cron) to build and publish to GitHub Pages. Output goes to `./dist`. The Vercel deployment (configured by `vercel.json`) mirrors the site and is the production host for the global-scores Function at `api/scores.ts` (see ADR 002).
